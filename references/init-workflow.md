# `init` 初始化与刷新流程

`$project-vibe-spec init` 用于建立项目治理基线，也用于后续刷新。它必须可重复执行：再次运行时更新已有映射、路由和交付状态，不重复创建同类目录，不覆盖仓库自己的规则和事实文档。

## 目标

一次 `init` 应完成三件事：

1. 找到项目当前已有的规则、事实来源、实现与验证入口。
2. 建立轻量的 Agent 路由，让后续任务只读取当前工作需要的文档。
3. 建立有证据的交付基线，把“已实现”“已验证”“计划中”和“待澄清”分开。

`init` 不负责根据代码反推产品需求，也不为了凑齐模板自动生成一套空 PRD/PDD。

## 第一步：发现现状

先检查工作区与仓库结构，再写任何文件。

至少读取：

- 当前工作目录适用的 `AGENTS.md`、`CLAUDE.md` 或其他项目指令文件；
- 根 README、贡献指南和 `docs/` 索引；
- 现有需求、决策、PRD、PDD、设计、业务流程、进度、发布说明；
- package/build/test/lint 配置、数据库 migration/schema、部署脚本等实现入口；
- 与已有文档声明相关的代表性代码和测试。

先看内容，再按职责归类。不能只靠文件名判断 `PRD.md`、`PDD.md`、`spec.md` 或 `design.md` 的含义。

## 第二步：给文档分类

把发现的资料归到以下类型：

- **项目规则**：长期适用的 Agent 行为、工程约束、安全边界和任务触发条件。
- **产品事实**：产品范围、用户行为、业务规则、验收口径。
- **技术事实**：架构、接口、数据、权限、运行时、兼容和发布约束。
- **设计事实**：UI、交互、设计 token、文案和响应式规则。
- **决策记录**：已经讨论过的方案、取舍和确认结果。
- **交付台账**：REQ、Bug、功能进度、项目进度。
- **参考/历史**：过期方案、spike、研究笔记、归档设计。

同一职责有多份文档时，识别哪一份是当前正本。无法判断时在地图中标为“待澄清”，不要自行选一份覆盖其他文档。

## 第三步：建立或刷新 `DOCUMENT_MAP.md`

优先沿用现有地图或索引。没有可用等价物时才创建 `DOCUMENT_MAP.md`。

地图至少记录：

- 职责；
- 实际路径；
- 类型；
- 当前状态；
- 什么时候应该读取或更新。

状态使用：`现行`、`参考`、`缺失`、`不适用`。

缺失职责先记为 `缺失`。只有当前项目或当前工作确实需要该职责时，才从模板创建文档。PRD/PDD 缺失本身不构成自动创建理由。

## 第四步：建立或刷新根 `AGENTS.md`

根 `AGENTS.md` 是 Agent 的工作入口和路由层，不是项目知识库。

保留仓库已有规则。只补齐以下内容：

- 所有任务都适用的工作边界；
- `DOCUMENT_MAP.md` 的入口；
- 按任务类型触发的阅读路由；
- 高风险操作的确认入口；
- 验证和 Git 的通用底线。

路由应写成“什么时候读哪份文档”，例如：

- 修改产品行为 → 需求记录 + PRD/产品规则；
- 修改 UI → UI/设计规范 + 对应产品规则；
- 修改 schema/migration → 数据/技术规则 + 关联 DEC；
- 修改 Agent/MCP/检索 → 技术设计 + 对应业务流程；
- 修 Bug → Bug 台账 + 受影响模块规则；
- 发布/打包 → 构建、发布和兼容规则。

不要把 PRD/PDD 正文、表结构、接口字段或当前进度复制进 `AGENTS.md`。

如果现有 `AGENTS.md` 已有等价路由，沿用并补缺。需要新增由本 Skill 维护的路由块时，可使用：

```md
<!-- project-vibe-spec:routes:start -->
...
<!-- project-vibe-spec:routes:end -->
```

以后重跑 `init` 只刷新这段，不改动块外内容。

目录级规则只有在以下条件同时满足时才创建嵌套 `AGENTS.md`：

- 规则只对该目录或模块长期有效；
- 根路由无法简洁表达；
- 当前 Agent 运行时支持目录级规则继承。

不要为每个目录批量生成 `AGENTS.md`。

## 第五步：补齐最小治理文件

模板只补当前需要且没有等价物的职责。

通常优先保证：

- 根 `AGENTS.md`；
- `DOCUMENT_MAP.md`；
- 已经存在非 Bug 工作时的需求台账；
- 已经存在重大技术/数据决策时的决策记录；
- 项目需要持续跟踪交付时的项目进度；
- 大任务已经开始时的功能进度记录。

Bug、PRD、PDD、UI Guide、Business Flow 等根据项目现状创建。不要因为模板里有文件就全部复制。

## 第六步：建立交付基线

如果项目需要项目总进度，沿用现有文件；缺失时可从 `assets/governance-starter/docs/PROGRESS.md.template` 创建。

进度必须区分证据强度：

- **已验证**：实现存在，并有符合项目要求的验证证据。
- **已实现待验证**：代码或配置已落地，但约定的验证尚未完成。
- **已通过（POC）**：只证明 POC 范围成立，不能当作正式版本完成。
- **进行中**：有明确 REQ，当前正在实现。
- **待开发**：已确认范围，尚未开始。
- **待拆分需求**：范围已知，但还没有可执行 REQ。
- **待澄清**：产品/技术事实不足，不能确定范围或完成条件。
- **不纳入**：已明确排除并记录原因。

代码可以证明“当前实现是什么”，不能单独证明“产品原本应该是什么”。没有 PRD 或用户确认时，不要把现有代码反推成产品需求或验收标准。

已有功能不需要为了初始化强行补历史 REQ。REQ 用于从当前治理基线开始追踪新增或仍在推进的工作。

## 第七步：检查冲突和缺口

初始化结束前检查：

- `AGENTS.md` 路由指向的路径是否都存在或明确标注缺失；
- `DOCUMENT_MAP.md` 是否出现同一职责两个“现行”正本；
- README、产品文档、技术文档和代码之间是否有明显冲突；
- 进度里的“已验证”是否有真实证据；
- 是否误把参考/历史文档当成现行规则；
- 是否创建了与已有目录重复的平行台账。

发现冲突时记录差异；会改变产品范围、数据语义、权限、安全、兼容性或成本的冲突交给用户确认。

## 第八步：交付初始化报告

向用户报告：

- 沿用了哪些已有规则和文档；
- 创建或更新了哪些文件；
- 根 `AGENTS.md` 新增了哪些任务路由；
- 当前项目的产品、技术、设计和交付事实来源分别在哪里；
- 哪些职责缺失或仍待澄清；
- 项目当前交付基线及其证据；
- 下一项最值得处理的缺口。

不要把“模板已创建”当作初始化完成。初始化完成的判断标准是：后续 Agent 能从根入口准确找到当前任务需要的规则和事实，并且不会把未知事项当成已确认事实。
