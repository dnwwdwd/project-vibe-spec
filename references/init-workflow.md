# `init` 初始化与刷新流程

`$project-vibe-spec init` 用于建立项目治理基线，也用于后续刷新。它必须可重复执行：再次运行时更新已有映射、路由和交付状态，不重复创建同类目录，不覆盖仓库自己的规则和事实文档。

## 目标

一次 `init` 应完成三件事：

1. 摸清项目当前已有的规则、事实来源、实现与验证入口。
2. 建立轻量的 Agent 路由，让后续任务直达当前工作所需的真实文档路径。
3. 建立有证据的交付基线，把“已实现”“已验证”“计划中”和“待澄清”清晰分开。

`init` 不负责根据代码反推产品需求，也不为了凑齐模板自动生成一套空 PRD/PDD。

## 第一步：发现现状与脚本审计

先检查工作区与仓库结构，再写任何文件。

若运行环境支持 Python 3，先在目标仓库执行只读审计脚本获取客观盘点：

```bash
python3 <skill-dir>/scripts/audit_governance.py <repo-path>
```

再按需读取：

- 当前工作目录适用的 `AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`.github/copilot-instructions.md` 等指令文件；
- 根 `README`、贡献指南和 `docs/` 索引；
- 现有需求、决策、PRD、PDD、设计、业务流程、进度、发布说明；
- package/build/test/lint 配置、数据库 migration/schema、部署脚本等实现入口；
- 与已有文档声明相关的代表性代码和测试。

先看内容，再按职责归类。不能只靠文件名猜测 `PRD.md`、`PDD.md`、`spec.md` 或 `design.md` 的实际角色。

## 第二步：给文档分类

把发现的资料归到以下类型：

- **项目规则**：长期适用的 Agent 行为、工程约束、安全边界和任务触发条件。
- **产品事实**：产品范围、用户行为、业务规则、验收口径。
- **技术事实**：架构、接口、数据、权限、运行时、兼容和发布约束。
- **设计事实**：UI、交互、设计 token、文案和响应式规则。
- **决策记录**：已经讨论过的方案、取舍和确认结果。
- **交付台账**：REQ、Bug、功能进度、项目进度。
- **参考/历史**：过期方案、spike、研究笔记、归档设计。

同一职责有多份文档时，识别哪一份是当前正本。无法判断时在地图中标为 `待澄清`，不要自行选一份覆盖或静默丢弃其他文档。

## 第三步：建立或刷新 `DOCUMENT_MAP.md`

优先沿用现有地图或索引；没有可用等价物时，从 `assets/governance-starter/DOCUMENT_MAP.md.template` 创建 `DOCUMENT_MAP.md`。

地图至少记录：职责、类型、当前状态、实际路径、读取/更新触发条件。

状态统一使用：`现行`、`参考`、`待澄清`、`缺失`、`不适用`（详见 [document-maintenance.md](document-maintenance.md)）。

缺失职责先记为 `缺失`。只有当前项目或当前工作确实需要该职责时，才从模板创建文档。PRD/PDD 缺失本身不构成自动创建理由。

## 第四步：建立或刷新根 `AGENTS.md`（含多指令文件策略）

根 `AGENTS.md` 是 Agent 的工作入口和路由层，不是项目知识库。

### 多指令文件并存处理

如果仓库已存在 `CLAUDE.md`、`.cursorrules` 或 `.github/copilot-instructions.md` 等其他 Agent 主规则文件，严禁复制一份平行正文导致双写漂移：

- **若仓库已以 `CLAUDE.md` 为主入口且团队依赖它**：可在确认或沿用前提下，让 `AGENTS.md` 只保存薄路由/入口并指向同一规范源（或反过来让另一文件仅做单行引用指向 `AGENTS.md`），保持规则正文只有单一出处。
- **若发现两份既有指令文件正文冲突**：记录到初始化报告的冲突清单，由用户裁定保留或合并方式，不静默覆盖。

### 路由内容与幂等标记

保留仓库已有规则，只补齐：全局工作边界、`DOCUMENT_MAP.md` 入口、按任务类型触发的阅读路由、高风险确认入口，以及通用验证和 Git 底线。

路由应尽量写入**仓库真实路径**（缺失项明确标注“缺失，见 `DOCUMENT_MAP.md`”），减少日常任务每次两跳查找的开销，例如：

- 修改产品行为 → `Requirements/LEDGER.md` + `docs/PRD.md`（若缺失则标注缺失）；
- 修改 UI → `docs/UI_GUIDE.md` + 对应产品事实；
- 修改 schema/migration → 技术/数据规则 + `Decisions/LEDGER.md`（先过方案确认）；
- 修改核心架构/异步通道/外部工具编排 → 技术事实 + 对应业务流程；
- 修 Bug → `docs/BUG_TRACKER.md` + 受影响模块规则；
- 发布/打包 → 构建、发布和兼容规则。

不要把 PRD/PDD 正文、表结构、接口字段或当前进度复制进 `AGENTS.md`。需要新增由本 Skill 维护的路由块时，使用幂等标记：

```md
<!-- project-vibe-spec:routes:start -->
...
<!-- project-vibe-spec:routes:end -->
```

以后重跑 `init` 只刷新标记块内内容，不改动块外用户规则。

目录级规则只有在“仅对单目录长期有效 + 根路由无法简洁表达 + 当前运行时支持目录级继承”同时满足时才创建嵌套 `AGENTS.md`，不要批量生成。

## 第五步：按需补齐最小治理文件

模板清单见 [document-maintenance.md](document-maintenance.md#模板资产索引assetsgovernance-starter)。模板只补当前需要且没有等价物的职责：

- 优先保证：根 `AGENTS.md`、`DOCUMENT_MAP.md`。
- 按需建立：已有非 Bug 工作时建需求台账；已有重大技术/数据决策时建决策记录；需要持续追踪交付时建项目总进度；大任务已启动时建功能进度。
- Bug、PRD、PDD、UI Guide、Business Flow 视项目现状决定，不把模板整包复制。
- 目录落位尊重仓库习惯：可采用默认结构，也可统一收拢到 `docs/` 下（如 `docs/requirements/`），在 `DOCUMENT_MAP.md` 如实映射即可。

## 第六步：建立交付基线

若项目需要项目总进度，沿用现有文件；缺失时从 `assets/governance-starter/docs/PROGRESS.md.template` 创建。

进度必须区分证据强度：

- **已验证**：实现存在，并有符合项目要求的验证证据。
- **已实现待验证**：代码或配置已落地，但约定验证尚未完成。
- **已通过（POC）**：只证明 POC 范围成立，不能当作正式版本完成。
- **进行中**：有明确 REQ，当前正在实现。
- **待开发**：已确认范围，尚未开始。
- **待拆分需求**：范围已知，但尚无可执行 REQ。
- **待澄清**：产品/技术事实不足，不能确定范围或完成条件。
- **不纳入**：已明确排除并记录原因。

代码只能证明“当前实现是什么”，不能单独证明“产品原本应该是什么”。没有 PRD 或用户确认时，不把现有代码反推成产品需求或验收标准。已有功能不强行倒补历史 REQ。

## 第七步：自动化校验与冲突检查

初始化结束前，先重跑只读审计脚本：

```bash
python3 <skill-dir>/scripts/audit_governance.py <repo-path>
```

再结合语义复核以下 6 项：

- `AGENTS.md` 路由指向的路径是否都存在或明确标注缺失，根文件是否保持精简未膨胀；
- `DOCUMENT_MAP.md` 是否出现同一职责两个 `现行` 正本，或存在非法状态；
- 是否存在多份互相矛盾的 Agent 指令文件；
- README、产品文档、技术文档和代码之间是否有明显冲突；
- 进度里的 `已验证` 是否有真实证据，是否存在未汇总的 `待方案确认` / `待实机回归`；
- 是否误把 `参考` 历史文档当成现行规则，或创建了与已有目录重复的平行台账。

发现冲突时如实记录差异；涉及产品范围、数据语义、权限、安全、兼容性或成本的冲突交给用户确认。

## 第八步：交付初始化报告

向用户报告：

- 沿用了哪些已有规则和文档（以及多指令文件的衔接方式）；
- 创建或更新了哪些文件；
- 根 `AGENTS.md` 新增或刷新了哪些任务路由；
- 当前项目的产品、技术、设计和交付事实来源分别在哪里；
- 哪些职责处于 `缺失` 或 `待澄清`；
- 项目当前交付基线及验证证据（含待实机回归项）；
- 审计脚本结果与下一项最值得处理的缺口。

初始化完成的判断标准不是“模板已创建”，而是：后续 Agent 能从根入口直达当前任务所需的规则和事实，且不会把未知事项当成已确认事实。
