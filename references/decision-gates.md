# 方案确认关卡

## 适用范围

以下情形先出方案、后实现：需求口径不完整；有多个合理实现方向；改变产品范围、权限、安全、公开 API 或兼容性；引入外部服务；影响难以回退；以及任何数据库表、DDL、迁移或等效 ORM schema 变更。

调查现状、阅读代码、编写待确认的需求/方案文档可以先做。未经确认，不能把待选方案写成产品行为、DDL、迁移、数据访问代码或接口事实。

## 通用方案说明

向用户展示的方案应能直接用于讨论，至少写清：

1. 已确认的目标、范围、不做项和验收标准。
2. 现有实现和业务流程中的相关事实、约束与依赖。
3. 可选方案、各自收益与代价。
4. 推荐方案及理由。
5. 实施步骤、风险、兼容性、验证和回退策略。
6. 尚待用户决定的问题。

用具体页面、流程、实体、接口和行为描述影响，避免只写“优化”“支持”“提升”等抽象结论。

## 数据设计方案

数据方案在通用内容外，必须逐项回答：

| 项目 | 需要说明的内容 |
|---|---|
| 业务语义 | 该数据代表什么、由谁创建/读取/修改/删除、保留多久 |
| 现状 | 现有表、字段、数据量/质量、读写路径和下游依赖 |
| 模型 | 实体关系、字段名、类型、可空性、默认值、主键/外键、唯一/检查约束、索引 |
| 方案比较 | 维持现表、扩字段、拆表/合表、关联表或其他可行方案的取舍 |
| DDL 草案 | 待确认的 schema diff 或 DDL；不能标示为已执行 |
| 迁移 | 顺序、锁表/性能影响、历史数据回填、双写或兼容窗口、发布次序 |
| 安全与生命周期 | 权限、敏感数据、审计、软删/硬删、保留和清理规则 |
| 风险控制 | 备份、监控、失败处理和可验证的回滚步骤 |

“用一个表还是多个表”“字段是否允许为空”“删除是否可恢复”都属于业务决策。不能由 Agent 以实现方便为由自行裁定。

## 确认和变更记录

- 将方案保存在关联的 REQ 或 DEC 中，状态标记为“待方案确认”。
- 用户确认时，记录确认的方案、日期、仍适用的前提和拒绝的替代方案。
- 方案实施中出现新事实导致字段语义、关系、迁移或影响范围变化时，状态退回“待方案确认”，更新方案后再次沟通。
- 用户授权实现不等于授权未展示的扩展、删除或数据处理行为。
