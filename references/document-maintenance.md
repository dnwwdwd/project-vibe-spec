## 文档体系与 `AGENTS.md` 边界

Project Vibe Spec 把项目资料分为四层：

1. **项目规则与路由**：根 `AGENTS.md` 和必要的模块级 `AGENTS.md`。
2. **文档地图**：`DOCUMENT_MAP.md`，只负责“什么职责现在由哪份文档承担”。
3. **事实与决策**：产品、技术、设计、业务流程和 DEC。
4. **交付记录**：REQ、Bug、项目进度和功能进度。

同一职责只应有一个 `现行` 正本。历史方案、研究文档、旧设计稿和 spike 标为 `参考`，不能与现行规则并列生效。

根 `AGENTS.md` 只保留：
- 所有任务都适用的仓库边界和安全底线；
- 文档地图入口；
- 尽量指向真实路径的“什么任务要读什么”触发路由；
- 高风险操作的确认入口，以及通用验证和 Git 底线。

不要放入根 `AGENTS.md`：PRD/PDD 正文、数据库表结构与接口字段、当前 sprint/临时需求/逐日进度、大段模块实现说明，或可由 lint/test/typecheck/script 强制执行的细则。

只适用于单个目录或模块的长期规则可放到嵌套 `AGENTS.md`；跨目录复用且需长篇解释的规则放到现行事实文档，再由根文件路由过去。

## `DOCUMENT_MAP.md` 与状态约定

地图记录职责、类型、状态、实际路径和读取/更新触发条件。状态统一使用以下 5 种：

- `现行`：当前权威来源，且路径必须存在。
- `参考`：历史、研究、草案或辅助资料，不作为现行约束。
- `待澄清`：同一职责存在多份候选文档或与实现存在重大冲突，需用户裁定当前正本。
- `缺失`：当前无明确事实来源，不得凭代码自行补写产品事实。
- `不适用`：项目明确不需要该职责，并记录理由。

地图不保存产品或技术结论，也不因模板默认路径改变仓库既有组织方式。首次接入和后续 `init` 均优先沿用现有目录。

## 事实文档、交付记录与状态机

| 类型 | 记录内容 |
|---|---|
| 产品事实 / PRD | 产品定位、范围、角色、行为、流程、权限口径、异常和验收 |
| 技术事实 / PDD | 架构、模块、接口、数据、权限实现、运行时、兼容、验证与发布 |
| 设计规范 | 视觉、交互、状态、组件、token、内容和响应式规则 |
| Business Flow | 指定业务域的入口、状态流、异常、边界和跨模块关系（状态与地图一致：`现行` / `参考`） |
| Decision Record (DEC) | 重大方案、备选项、取舍、确认结果、适用前提和恢复口径 |
| Requirements Ledger / Record | 从治理基线开始的非 Bug 需求总表，及跨模块/复杂需求的详细记录 |
| Bug Tracker | 现象、影响范围、根因、修复与可验证用户行为 |
| Project Progress | 项目交付基线、里程碑、证据、回归门槛和下一步 |
| Feature Progress (PROG) | 大任务的阶段计划、DoD、证据、阻塞和下一步 |

已有功能不要求为了初始化倒补历史 REQ；REQ 追踪从治理基线开始新增或仍在推进的工作。

### 统一状态机约定

- **需求（REQ）**：`待澄清` → `待方案确认` → `已确认待排期` → `进行中` / `已阻塞` → `待验证` → `已完成`（或 `已取消`）。
- **决策（DEC）**：`待方案确认` → `已确认待实施` → `实施中` → `已实施待验证` → `已完成`（或 `已取消`）。用户确认前不得脱离 `待方案确认`。
- **Bug**：`待定位` → `待修复方案确认`（需确认方案时）→ `修复中` → `待验证` → `已验证关闭`；临时止血用 `已缓解`，确认不修用 `不予修复`（附理由）。**实现完成但尚未通过约定验证时停留在 `待验证`，不得直接标关闭。**
- **功能进度（PROG）**：`待开始` → `进行中` / `已阻塞` → `待验证` → `已完成`（或 `已取消`），与关联 REQ 状态保持联动。
- **项目总进度基线**：`已验证`、`已实现待验证`、`已通过（POC）`、`进行中`、`待开发`、`待拆分需求`、`待澄清`、`不纳入`。

### “待实机回归”收口规则

真实平台、凭据、外部服务或硬件环境受限时，记录“待实机回归”的具体用户路径、受限原因与验证条件：

1. 对应 REQ / Bug / PROG 状态**停留在 `待验证`**，不得提前标记 `已完成` 或 `已验证关闭`。
2. 若仓库存在项目总进度，将其同步汇总到“发布与回归门槛”的回归清单，并在交付报告中单列，避免埋在单项记录中遗忘。
3. 后续环境就绪并完成真实用户路径验证后，补录证据再转入终态。

## 更新原则与矩阵

只在“事实或状态真的变化”时更新对应正本；没有变化时不要为了“同步”机械改文档。

| 变化类型 | 必须检查 | 常见联动更新 |
|---|---|---|
| 新功能 / 功能优化 | 产品事实、REQ | 技术事实、设计规范、Business Flow、DEC、Progress |
| UI / 交互 / 文案 | 设计事实、产品事实 | REQ、技术事实、Progress |
| 架构 / 数据 / API / 异步或工具编排 | 技术事实、DEC、REQ | 产品事实、Business Flow、Progress |
| Bug 修复 | Bug 台账 | 若修复改变了现行产品或技术事实，同步对应正本 |
| 仅构建 / 打包 | 构建与发布规则 | 发布说明（默认不建 REQ） |

## 跨模块判定与验收要求

满足以下任一架构特征时，非 Bug 需求必须建立详细 REQ（跨模块 Bug 仍记入 Bug 台账，但须补齐影响范围与可验证用户行为）：

- **多写/多读持久化资源**：同一数据实体或文件有多个写入入口或多个消费方。
- **跨通道状态传播**：状态跨 HTTP/RPC API、流式推送/长连接（如 SSE/WebSocket）、缓存、本地存储、消息队列或后台任务传播。
- **跨工具/插件或 AI 编排边界**：涉及 Agent 编排、工具/插件扩展（如 Skill/MCP）、检索/索引管道或多媒体/文件处理链路。
- **跨端/安全/环境边界**：涉及多个运行时或客户端平台、权限边界、凭据/密钥管理或外部第三方服务。

详细 REQ 至少记录：写入入口；读取方与刷新/恢复路径；失败、取消、回滚与安全/平台边界；已检查但不受影响的模块；以及行为验收矩阵。

## 记录关系、编号与规模治理

- **双向关联**：重大决策关联 REQ（或注明为项目级长期决策）；大任务 REQ 与功能进度记录双向链接；项目进度引用 REQ/DEC/测试/构建结果作为证据，不复制事实正文。
- **证据红线**：`已验证` 必须有真实证据；仅有代码落地时最多写 `已实现待验证`；POC 只写 `已通过（POC）`，不能直接升级为正式交付完成。
- **编号与并行协作**：若项目已使用 GitHub Issues、Linear、Jira 等外部编号，优先沿用外部 ID（如 `#123`、`LIN-45`），不另造流水号。使用内置 `REQ/DEC/BUG-YYYYMMDD-NNN` 在多分支并行撞号或 `LEDGER.md` 合并冲突时，以合入主分支顺序重排并同步链接。
- **目录落位**：模板默认给出一套扁平路径，但全新仓库若希望保持根目录整洁，可将 `Requirements/`、`Decisions/`、`Progress/` 与其他文档统一收拢到 `docs/`（如 `docs/requirements/`）下，在 `DOCUMENT_MAP.md` 中如实映射即可。
- **防台账膨胀**：`BUG_TRACKER.md` 等单文件台账在条目过多（如超过 20 条已关闭项）或出现复杂跨模块 Bug 时，可将已关闭旧记录归档或将复杂 Bug 拆为独立文件并在台账中链接。

## 模板资产索引（`assets/governance-starter/`）

仅在仓库缺少对应职责且当前确实需要时按需复制对应模板：

| 模板路径 | 对应职责 | 典型创建时机 |
|---|---|---|
| `AGENTS.md.template` | 根 Agent 入口与任务路由 | 无 `AGENTS.md` 且无既有等价主规则时 |
| `DOCUMENT_MAP.md.template` | 文档地图 | 无文档地图/索引时 |
| `Requirements/LEDGER.md.template` | 需求总台账 | 开始持续追踪非 Bug 需求时 |
| `Requirements/README.md.template` | 需求目录说明 | 创建独立 `Requirements/` 目录时 |
| `Requirements/REQ-YYYYMMDD-NNN.md.template` | 详细需求记录 | 跨模块、复杂或大任务需求 |
| `Decisions/LEDGER.md.template` | 决策总台账 | 需要追踪数据/架构/高风险决策时 |
| `Decisions/README.md.template` | 决策目录说明 | 创建独立 `Decisions/` 目录时 |
| `Decisions/DEC-YYYYMMDD-NNN.md.template` | 单项决策记录 | 涉及 DDL/迁移、架构、API 或难回退选择 |
| `Progress/LEDGER.md.template` | 功能进度总台账 | 开始追踪大任务功能进度时 |
| `Progress/README.md.template` | 功能进度目录说明 | 创建独立 `Progress/` 目录时 |
| `Progress/PROG-REQ-YYYYMMDD-NNN-slug.md.template` | 单项大任务功能进度 | 多阶段/多轮会话大任务 |
| `docs/PROGRESS.md.template` | 项目总进度与交付基线 | 项目需要持续维护交付基线与里程碑时 |
| `docs/BUG_TRACKER.md.template` | Bug 台账 | 需要集中追踪缺陷与验证证据时 |
| `docs/PRD.md.template` | 产品事实 / PRD | 用户明确要求新建产品事实文档时 |
| `docs/PDD.md.template` | 技术事实 / PDD | 用户明确要求新建技术设计文档时 |
| `docs/UI_GUIDE.md.template` | 设计与 UI 规范 | 项目有前端/界面且需沉淀设计规则时 |
| `docs/BUSINESS_FLOW.md.template` | 指定业务域流程 | 存在需梳理的复杂/跨模块核心链路时 |
