# 文档维护规则

## 文档体系

Project Vibe Spec 把项目资料分为四层：

1. **项目规则与路由**：根 `AGENTS.md` 和必要的模块级 `AGENTS.md`。
2. **文档地图**：`DOCUMENT_MAP.md`，只负责“什么职责现在由哪份文档承担”。
3. **事实与决策**：产品、技术、设计、业务流程和 DEC。
4. **交付记录**：REQ、Bug、项目进度和功能进度。

同一职责只应有一个“现行”正本。历史方案、研究文档、旧设计稿和 spike 标为“参考”，不能和现行规则并列使用。

## `AGENTS.md` 的职责

根 `AGENTS.md` 只保留：

- 所有任务都适用的仓库边界和安全底线；
- 文档地图入口；
- “什么任务要读什么”的触发路由；
- 通用验证和 Git 规则。

不要放入：

- PRD/PDD 正文；
- 数据库表结构和接口字段；
- 当前 sprint、临时需求和逐日进度；
- 大段模块实现说明；
- 可以由 lint/test/typecheck/script 强制的细则。

只适用于单个目录或模块的长期规则，可以放到嵌套 `AGENTS.md`；跨目录复用、需要长篇解释的规则放到现有事实/规则文档，再由根文件路由过去。

## `DOCUMENT_MAP.md` 的职责

地图记录职责、类型、状态、真实路径和触发条件。状态使用：

- `现行`
- `参考`
- `缺失`
- `不适用`

地图不保存产品或技术结论，也不因为模板默认路径改变仓库自己的组织方式。

首次接入和后续 `init` 都先沿用现有目录。只有项目当前确实需要、且仓库没有等价来源的职责才创建模板。

## 事实与交付文档

| 类型 | 记录内容 |
|---|---|
| 产品事实 / PRD | 产品定位、范围、角色、行为、流程、权限口径、异常和验收 |
| 技术事实 / PDD | 架构、模块、接口、数据、权限实现、运行时、兼容、验证与发布 |
| 设计规范 | 视觉、交互、状态、组件、token、内容和响应式规则 |
| Business Flow | 指定业务域的入口、状态流、异常、边界和跨模块关系 |
| Decision Record | 重大方案、备选项、取舍、确认结果、适用前提和恢复口径 |
| Requirements Ledger | 从治理基线开始的非 Bug 需求状态和关联记录 |
| Requirement Record | 复杂/跨模块需求的范围、影响、方案、验收和证据 |
| Bug Tracker | 现象、影响、根因、修复和验证 |
| Project Progress | 项目交付基线、里程碑、证据和下一步 |
| Feature Progress | 大任务的阶段、DoD、证据、阻塞和下一步 |

已有功能不要求为了初始化倒补历史 REQ。REQ 追踪初始化之后新增或仍在推进的工作。

## 更新原则

只在“事实或状态真的变化”时更新对应正本。

| 变化 | 必须检查 | 常见更新 |
|---|---|---|
| 新功能 / 功能优化 | 产品事实、REQ | 技术事实、设计、Flow、DEC、Progress |
| UI / 交互 / 文案 | 设计事实、产品事实 | REQ、技术事实、Progress |
| 架构 / 数据 / API / Agent / 检索 | 技术事实、DEC、REQ | 产品事实、Flow、Progress |
| Bug 修复 | Bug 台账 | 若修复改变现行事实，再更新对应正本 |
| 仅构建 / 打包 | 构建发布规则 | 发布说明 |

不需要更新的文档不要为了“同步”机械改动。

## 跨模块记录与验收

满足任一条件时，非 Bug 需求建立详细 REQ：同一持久化资源有多个写入入口或读取方；状态跨 API、SSE、缓存或后台任务传播；涉及 Agent、检索、索引、图片、文件、Skill、MCP；涉及多个运行时/平台、权限或密钥。

至少记录：

- 写入入口；
- 读取方、刷新和恢复路径；
- 失败、取消、回滚、安全和平台边界；
- 已检查但不受影响的模块；
- 行为验收矩阵。

跨模块 Bug 仍记录到 Bug 台账，但补充影响范围和可验证的用户行为。

## 记录关系

- 重大决策关联 REQ 或明确说明为何是项目级长期决策。
- 大任务 REQ 链接功能进度记录，功能进度记录反向链接 REQ。
- 项目进度可以引用 REQ/DEC/测试/构建结果作为证据，但不复制事实文档正文。
- “已验证”必须有真实证据；只有代码存在时最多写“已实现待验证”。
- POC 只写“已通过（POC）”，不能直接升级成正式版本完成。
